# Ollmin 产品方案与分阶段构建计划

> 工作名称：**Ollmin**。一个面向 Windows 低性能设备与本地小模型的 Ollama 原生聊天客户端。
>
> 本文保留最初的产品与阶段规划，是过程性历史文档。当前实现请以 [ARCHITECTURE.md](../../ARCHITECTURE.md) 和 [DECISIONS.md](../../DECISIONS.md) 为准。文内旧目录树反映编写时的结构。

## 当前实现快照（2026-09-09）

- 已实现本机 Ollama 检测、模型列表/预热、原生流式聊天、停止、性能档位、4K/8K/16K 上下文设置、独立输出/推理预算和本地会话管理；当前连接端点固定为 `127.0.0.1:11434`。
- 已实现 PDF、DOCX、XLS/XLSX 本地附件解析与按消息归属的受限上下文引用；这不是知识库或跨会话 RAG；
- 已实现 Rust 流批处理、前端动画帧合并、安全 Markdown、模型别名、自定义标题栏和 Debug/显式诊断；
- 已有 Rust 单元测试与 Vitest 组件/工具测试；没有完整 Playwright 桌面 E2E，且没有将历史计划中的性能目标写作当前已验证结果；
- 当前 Tauri bundle 关闭，普通 Debug/Release 构建不生成 MSI/NSIS 安装包。

## 1. 产品结论

Ollmin 不做“功能更全的 Chatbox”，而做“**让本地 Ollama 的一次聊天尽可能接近 `ollama run` 体验**”的桌面应用。

核心价值是消除非必要等待，而不是声称提高同一模型、同一硬件的原始推理速度：

- 少发 token：短系统提示词、受控历史、不开启无关工具定义；
- 少等冷启动：模型预热和可配置常驻；
- 不抢资源：同一模型默认只有一个前台生成任务；
- 少做后台推理：不自动生成标题、摘要、记忆或向量索引；
- 看得见差异：每轮都展示加载、提示词预填充、生成速度等原始指标。

首发目标为已安装 Ollama、使用 Qwen3-4B 等小模型的 Windows 10/11 用户。应用只连接本机 `127.0.0.1:11434`，不需要账号、云端 API Key 或联网服务。

## 2. 问题定义与产品原则

### 2.1 为什么 GUI 常常比 CLI 慢

CLI 与 GUI 的“同一个问题”往往并不是同一个请求。常见额外成本包括：完整会话历史、冗长系统提示词、工具/MCP 定义、后台标题生成、多个并发请求，以及模型被卸载后的重新加载。

Qwen3 默认具有思考模式。它会先产生思考 token，再给出正文；在小模型或 CPU 推理场景下，简单问答开启思考会明显拉长端到端时间。Ollama 的原生 Chat API 支持单请求 `think: false`，因此客户端可以明确区分快速对话和推理任务。

上下文长度和并发还会共同放大内存压力。Ollama 的默认上下文为 4K；其并发请求内存需求随 `OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH` 增长。对低配设备，长上下文、后台任务和并发是需要主动避免的三类负担。

### 2.2 不可妥协的原则

1. **本地优先**：首版不发送提示词、聊天记录、硬件信息或统计数据到网络。
2. **性能可解释**：每次慢都应能区分是排队、模型加载、提示词预填充、思考 token 还是正文生成慢。
3. **默认克制**：任何会额外调用模型的功能必须显式开启，并说明成本。
4. **原生优先**：直接使用 Ollama `/api/*`，而非以 OpenAI 兼容层作为核心通路。
5. **低风险**：不执行模型生成的命令、不提供网页访问、MCP、插件或自动化工具调用。

## 3. 用户、场景与边界

| 用户      | 场景                       | 成功标准                  |
| ------- | ------------------------ | --------------------- |
| 本地模型新用户 | 日常问答、翻译、改写               | 输入后立即看到流式首字，默认不会“想很久” |
| 低配笔记本用户 | CPU、核显或小显存设备上运行 1B–8B 模型 | 不因客户端本身占用或并发而额外卡顿     |
| 本地开发者   | 比较模型、参数与客户端开销            | 能导出或查看每轮真实性能数据        |
| 需要推理的用户 | 代码解释、分析、复杂问题             | 可一键开启思考并明确等待成本        |

### 3.1 第一版（MVP）包含

- 本机 Ollama 连接检测、模型列表，以及已加载模型查询能力；
- 单模型单会话聊天、流式 Markdown 文本输出、停止生成、复制；
- 快速/平衡/推理三个性能档位；
- 会话历史的本地保存、重命名、删除、导出；
- 模型预热、常驻策略、受控历史裁剪；
- 单轮性能仪表与 Debug/显式开启的本地诊断；
- 中文优先界面、深色/浅色主题、基础无障碍键盘操作。
- PDF、DOCX、XLS/XLSX 本地附件的受限解析和按消息引用。

### 3.2 明确不做

- RAG、文档索引、知识库、嵌入模型；
- 网页搜索、云模型、账号体系、同步与遥测；
- MCP、插件、Agent、多步骤工具调用、Shell/文件执行；
- 图像、语音、联网协作与手机端；
- 自动标题、自动摘要、自动长期记忆。

这些能力并非无价值，但它们会引入额外模型调用、上下文膨胀、隐私边界和资源竞争，与 MVP 的性能定位冲突。

## 4. 体验设计

### 4.1 主界面

```text
┌ 会话列表 ──────────┬──────────────── 对话 ────────────────┐
│ + 新建              │ 模型：qwen3:4b  [快速 v] [常驻]      │
│ 会话 A              │                                      │
│ 会话 B              │ 用户消息 / 模型流式回答               │
│                     │                                      │
│                     │ ─ 本轮：首字 0.8s | 21.4 tok/s ─     │
│                     │                                      │
│                     │ [输入消息…]                    [发送] │
└─────────────────────┴──────────────────────────────────────┘
```

- 默认界面只显示必要信息；“性能详情”折叠显示，避免干扰普通聊天。
- 流式到达的思考内容和正文分开处理。快速档不显示思考；推理档允许折叠查看。
- 生成中按钮变为“停止”；再次发送不与当前请求并发，用户可选择停止后发送或排队。
- 会话标题初始为“新对话”，仅在用户手动修改时更新；不发额外模型请求。

### 4.2 三个性能档位

| 档位     | 适用任务           | 请求策略                           | 取舍                       |
| ------ | -------------- | ------------------------------ | ------------------------ |
| 快速（默认） | 问答、翻译、改写、短代码片段 | `think: false`；4K 上下文；较短输出上限   | 速度优先，复杂推理质量可能下降          |
| 平衡     | 普通多轮讨论         | 允许思考；4K 上下文；中等输出上限             | 质量和等待时间折中                |
| 推理     | 复杂分析、代码排错      | `think: true`；可选 8K 上下文；较长输出上限 | 可能产生大量思考 token，占用更多内存与时间 |

档位是可见的请求配置，不是“魔法优化”。当前高级设置允许修改输出上限、推理上限和上下文上限；温度由后端固定为 `0.7`，尚未提供用户设置项。选择 8K/16K 上下文或开启推理会增加内存与时延风险，应在界面和文档中持续明确说明。

### 4.3 历史裁剪

1. 永远保留当前系统提示词和最近用户问题；
2. 在估算的 token 预算内，按时间倒序加入最近完整消息对；
3. 超预算时丢弃最早的完整消息对，不截断单条消息；
4. 不自动摘要旧消息。用户可手动选择“摘要并压缩”，该操作会单独显示一次模型调用成本；MVP 默认不实现该按钮；
5. 发送后根据 Ollama 返回的 `prompt_eval_count` 校正本地估算。

## 5. 技术架构

### 5.1 技术选型

- **桌面壳**：Tauri 2。Windows 使用系统 Microsoft Edge WebView2，应用不随包携带独立 Chromium 运行时，适合轻量桌面分发。
- **界面**：React + TypeScript + Vite；只使用受控状态与虚拟化会话列表，不引入重量级编辑器、图表或富文本框架。
- **本地后端**：Rust（Tauri command/event + `reqwest`）；负责 HTTP 流、取消、串行调度、错误归一化与统计解析。
- **数据**：SQLite（本地单文件）保存会话、设置和已发送附件的解析片段；知识库索引不在当前范围内。
- **测试**：当前有 Rust 单元测试和 React/Vitest 组件测试；完整 Playwright 桌面端到端测试仍未建立。真实 Ollama 使用本机模型做手工或基准验证，不纳入离线单元测试断言。

### 5.2 请求通路

```text
用户发送
  → 前端校验与历史裁剪
  → Rust 单活动请求调度器（默认并发 1）
  → POST http://127.0.0.1:11434/api/chat（stream: true）
  → NDJSON 流解析
  → Tauri event 增量发送至界面
  → 完成包中的统计数据写入 SQLite 并显示
```

Rust 后端而非前端 WebView 直连 Ollama，原因是：统一处理流、取消和错误；避免 WebView 跨域差异；可以阻止用户配置为非本机 URL；并能保证性能数据来自同一个请求。

### 5.3 Ollama 接口约定

启动时调用：

- `GET /api/tags`：读取本地模型；
- `GET /api/ps`：读取已加载模型、处理器和上下文；
- `POST /api/chat`：唯一的聊天主通路；
- 仅在用户点击时使用 `POST /api/generate` 空请求进行预热；
- 绝不在后台轮询生成接口。

快速档请求示意：

```json
{
  "model": "qwen3:4b",
  "messages": [{"role": "user", "content": "你好"}],
  "stream": true,
  "think": false,
  "keep_alive": "30m",
  "options": {
    "num_ctx": 4096,
    "num_predict": 2048,
    "temperature": 0.7
  }
}
```

原始规划曾提出对 `think` 做版本兼容检测并以 Qwen3 `/no_think` 作为临时降级方案；当前实现直接发送 `think` 字段，尚未实现该兼容降级。不能把该规划描述为已完成能力。

### 5.4 关键模块与目录规划

以下为早期重构设想，不代表完整的未来目录；当前 Ollmin 仍以 `src/App.tsx`、`src-tauri/src/commands.rs`、`src-tauri/src/chat.rs`、`src-tauri/src/platform/`、`storage.rs` 和 `attachments.rs` 共同实现。

```text
ollmin/
  src/                         # React UI
    features/chat/              # 会话、流式渲染、历史裁剪
    features/models/            # 模型状态、性能档位、预热

    features/settings/          # 本地设置
    shared/                     # 类型、格式化、无业务组件
  src-tauri/
    src/ollama/                 # API 客户端、NDJSON 解析、兼容层
    src/scheduler/              # 单活动请求调度、取消、常驻控制
    src/store/                  # SQLite 迁移与仓储
    src/commands/               # 最小 Tauri IPC 面
  tests/

    plan.md
    tests/benchmark-protocol.md
    privacy.md
```

## 6. 性能策略与可量化目标

### 6.1 先测量，再优化

应用必须区分以下指标，而不是只显示“耗时”：

| 指标           | 数据来源                                         | 用途             |
| ------------ | -------------------------------------------- | -------------- |
| 排队时间         | 本地调度器                                        | 判断是否有并发资源竞争    |
| 首字时间（TTFT）   | 前端时钟                                         | 用户感知延迟         |
| 模型加载时间       | `load_duration`                              | 判断模型是否常驻       |
| 提示词 token/耗时 | `prompt_eval_count` / `prompt_eval_duration` | 判断历史、系统提示词是否过长 |
| 输出 token/耗时  | `eval_count` / `eval_duration`               | 计算真实生成 tok/s   |
| 思考 token     | 流中的 `thinking` 字段                            | 判断是否为思考模式导致的等待 |

成功目标（在同一台机器、同一模型、同一请求和模型已预热的前提下）：

- Ollmin 相对直接调用原生 `/api/chat` 的额外首字开销不超过 150 ms；
- 空闲时不触发任何 LLM 请求；
- 同一模型默认前台生成并发为 1；
- 快速档不会发送工具定义、自动标题或完整历史；
- 用户能在一个界面确认本轮慢的主因。

这些是客户端开销目标；模型本身 tok/s 受 CPU、GPU、内存带宽、量化和模型卸载比例影响，不作为产品可承诺的固定数值。

### 6.2 资源保护策略

- 首次启动不自动预热；用户点击预热或发送首条消息后才加载模型。
- 当前请求固定 `keep_alive: "30m"`；没有暴露省内存 `5m` 档位；退出应用时默认不主动停止模型，避免影响其他客户端。
- 全局仅允许一个活动请求，避免低显存设备发生换入换出。
- 设置可选 4K/8K/16K；较大上下文会增加资源消耗，当前不提供无限选项。
- 后端保留按需 `/api/ps` 查询能力；当前主界面未展示定期或手动加载模型状态面板。
- 点击停止会通过 Rust `CancellationToken` 中断流；取消后不把部分回答自动作为后续上下文，除非用户保留。

## 7. 本地数据、隐私与安全

### 7.1 数据模型

| 实体                   | 核心字段                            | 说明                   |
| -------------------- | ------------------------------- | -------------------- |
| `settings`           | 主题、默认档位、常驻策略、端口                 | 仅本地配置                |
| `conversations`      | id、标题、模型、创建/更新时间                | 一个聊天会话               |
| `messages`           | 会话 id、角色、内容、思考内容、状态             | 保留原始可见文本；思考保存由用户设置决定 |
| `generation_metrics` | 消息 id、时间、load/prompt/eval 指标、档位 | 用于诊断，不含原始提示词副本       |

数据库放在操作系统的应用数据目录，使用 SQLite 事务与版本化迁移。导出文件由用户指定路径；删除会话必须提供确认，并从数据库永久删除相关记录。

### 7.2 安全边界

- 仅允许 `http://127.0.0.1:11434` 和 `http://localhost:11434`；设置页不提供任意远程 URL。
- 不能把 Ollama 绑定到局域网，也不修改 `OLLAMA_HOST`、防火墙或系统环境变量。
- 禁止模型调用工具，禁止根据模型输出执行命令、读取文件或发起网络请求。
- 不内置埋点、崩溃上报或自动更新检查；如果未来加入，必须独立开关、说明数据内容并默认关闭。
- 对 Markdown 严格转义 HTML，不渲染不可信脚本或嵌入式网页。

## 8. 分阶段构建计划

以下是历史实施路线，不能作为当前完成状态的证据。其与当前实现的对应关系如下：

| 历史阶段 | 当前状态 |
| --- | --- |
| 阶段 0–3：基线、聊天、性能、会话 | 主要能力已实现；完整性能基准结论需按测试协议重新采集 |
| 阶段 4：发布前验证与打包 | Debug/Release 可执行文件已验证；完整 E2E、签名和默认安装包不在当前实现范围 |
| 附件能力 | 原始路线未列入 MVP，现已作为单次消息附件实现 |

### 阶段 0：基准与工程基线（1–2 人日）

**目标**：用数据证明慢在哪里，避免先入为主地重写客户端。

- 初始化 Tauri + React + TypeScript 项目、格式化、lint、测试与 CI；
- 编写 `docs/tests/benchmark-protocol.md`：冷启动、预热后短问答、长历史、思考开/关四组测试；
- 实现只读诊断原型：`/api/tags`、`/api/ps`、单次 `/api/chat` 的指标采集；
- 在同一模型、同一提示词下，记录 CLI、原生 API、Chatbox/WorkBuddy（如可配置）的请求差异；
- 确认本机模型名、量化、处理器卸载比例、上下文与可用硬件。

**验收**：生成一份不含提示词正文的基准报告，能说明至少一次慢请求属于加载、预填充、思考、生成或排队中的哪一类。

### 阶段 1：可用的最小聊天闭环（2–3 人日）

**目标**：在没有性能“黑盒”的前提下完成可靠的单会话聊天。

- 实现 Ollama 原生 Chat 客户端、NDJSON 流解析和错误提示；
- 实现模型选择、输入、发送、停止、复制、Markdown 渲染；
- 实现快速/平衡/推理档位以及请求配置映射；
- 实现流式正文与思考内容的分离；
- 默认单请求调度，覆盖断线、服务未启动、模型不存在、取消等错误；
- 为流解析、档位映射、取消逻辑补充单元测试。

**验收**：Qwen3-4B 可以在本机连续进行至少 10 次短对话；快速档请求明确发送 `think: false`；停止按钮能终止当前流，界面不冻结。

### 阶段 2：低配性能能力（2–3 人日）

**目标**：把“快”变成可验证、可调节的产品能力。

- 实现历史 token 预算、成对裁剪与预算提示；
- 实现模型预热、`keep_alive`、省内存模式和显式模型状态刷新；
- 实现每轮性能仪表、诊断面板和可复制的匿名文本报告；
- 实现队列状态、取消后清理和防止后台请求；
- 对 4K/8K、思考开关、冷/热模型做回归基准；
- 后续建立 Playwright 后，再跑通发送、流式输出、停止、切档、离线错误五条主流程；当前尚未具备该流程。

**验收**：预热后的 Ollmin 与原生 API 在相同请求下达到“额外 TTFT 不超过 150 ms”的目标；性能面板能正确展示 Ollama 返回的统计字段。

### 阶段 3：本地会话与可用性（2 人日）

**目标**：让应用能作为日常工具使用，仍不破坏性能边界。

- SQLite 迁移、会话创建/重命名/删除/搜索、消息恢复；
- 手动导出 Markdown/JSON、可选清除本地数据；
- 设置页、主题、快捷键、键盘焦点和空状态；
- 思考内容是否落盘的独立设置，默认仅保留正文；
- 数据库迁移与删除级联测试。

**验收**：重启后会话与指标可正确恢复；删除会话不会遗留关联消息；离线运行时无外部网络请求。

### 阶段 4：发布前验证与打包（1–2 人日）

**目标**：在目标低配环境中可靠安装和运行。

- 开发、打包版分别做冒烟测试；
- 在 CPU 推理、部分 GPU 卸载和完全 GPU 卸载（如硬件具备）下复测基准；
- 运行端到端测试、依赖审查、Windows Defender 误报检查；
- 编写 README、隐私说明、故障排查和问题报告模板；
- 产出签名前的 MSI/NSIS 安装包与校验值。

**验收**：全套自动化测试通过；打包版可在无网络环境下连接已安装的本地 Ollama；没有访问远程服务的行为。

## 9. 测试策略

| 层级             | 重点                    | 例子                     |
| -------------- | --------------------- | ---------------------- |
| Rust 单元测试      | NDJSON、指标解析、请求映射、历史裁剪 | 最终 `done` 包正确落库        |
| React 组件测试     | 流式状态、停止状态、性能展示        | thinking 与 content 不混排 |
| 集成测试           | 本地模拟 Ollama HTTP 服务   | 503、断流、超时、取消           |
| Playwright E2E | 用户主路径                 | 发送、停止、切换档位、恢复会话        |
| 手工性能回归         | 真实模型与目标硬件             | 冷/热、4K/8K、思考开/关        |

性能测试必须固定模型版本、量化、提示词、上下文、是否预热和运行中的其他模型；只比较同一条件下的中位数与 P95，禁止用不同请求的“体感速度”做结论。

## 10. 风险与决策点

| 风险                        | 影响               | 应对                                    |
| ------------------------- | ---------------- | ------------------------------------- |
| 模型本身主要在 CPU 上运行           | 客户端优化无法改变低 tok/s | 用 `/api/ps` 显示处理器/上下文，诚实区分模型瓶颈        |
| Ollama 版本不支持或异常处理 `think` | 快速档可能仍输出思考       | 功能探测、明确降级提示、提供 Qwen3 指令级备用路径          |
| WebView2 在极低内存设备占用仍明显     | GUI 仍不如终端轻       | 维持单窗口、简单 DOM；阶段 0 实测后可评估纯原生 UI 作为后续方案 |
| 用户需要 RAG/MCP              | 容易扩大范围并降低速度      | 作为独立的“扩展版”路线，不进入 MVP                  |
| 客户端比较不公平                  | 错误归因、无效优化        | 固化基准协议，统一请求与预热状态                      |

以下决策在阶段 0 后确认：默认 `keep_alive` 时长、是否将 8K 作为可见选项、是否保存思考内容、最低 Windows 版本，以及是否需要兼容非 Qwen3 模型的思考配置。

## 11. 后续路线（不承诺进入首发）

当 MVP 的性能与稳定性通过验证后，再按用户价值评估：多模型预设、手动摘要压缩、图片输入、受限的本地文件问答、局域网只读连接。每项都必须单独评估新增的 token、内存、权限和隐私成本，不能默认开启。
