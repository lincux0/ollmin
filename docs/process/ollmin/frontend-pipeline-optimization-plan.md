# Ollmin 前端链路低延迟优化方案

> 实施状态（2026-09-09）：阶段 0 的诊断开关、阶段 1 的前端流合并、阶段 2 的消息记忆化、阶段 3 的 Rust 侧批处理，以及阶段 4 的共享 `reqwest::Client` 已体现在当前代码中。本文保留优化设计和验证方法；没有在本文中记录的 Release A/B 数据，不得视为已经完成性能验收。

## 1. 文档目的

本方案针对 Ollmin 从 Ollama 等价流式 API 到真实客户端前端之间的延迟和卡顿问题，目标是在不改变模型参数、思考策略、历史裁剪规则和本地优先边界的前提下，降低 Tauri IPC、React 更新和 Markdown 渲染造成的额外开销。

本方案只优化客户端链路，不把模型解码速度问题包装成前端优化结果。每个阶段都要求与 Ollama 服务端指标对照，区分模型耗时和客户端耗时。

## 2. 历史基线与问题定位

当前实际调用路径如下：

```text
Ollama /api/chat NDJSON
  -> Rust reqwest bytes_stream()
  -> 逐行解析与 ChatStreamEvent 构造
  -> app.emit("chat:chunk")
  -> React listen()
  -> 每个分片 setMessages()
  -> App 整体重渲染
  -> 思考区布局 + MarkdownContent 全量解析
```

已确认的关键位置：

- Rust 流读取和逐行分片发送：[chat.rs](../../../src-tauri/src/chat.rs)；
- Tauri 事件封装和事件批处理：[chat.rs](../../../src-tauri/src/chat.rs)；
- 前端逐分片状态更新：[App.tsx](../../../src/App.tsx)；
- 思考和正文同时更新：[App.tsx](../../../src/App.tsx)；
- 每次重新解析 Markdown：[MarkdownContent.tsx](../../../src/components/MarkdownContent.tsx)；
- 发送前的会话创建、用户消息保存和会话列表刷新：[App.tsx](../../../src/App.tsx)；
- `start_chat` 启动后台任务后立即返回：[commands.rs](../../../src-tauri/src/commands.rs)。

当前主要风险按优先级排序：

1. 每个 Ollama 分片都触发一次 Tauri 事件和 React 更新；
2. 流式更新时整个消息列表参与渲染，历史 Markdown 没有组件级记忆化；
3. 思考区持续增长，造成 WebView 布局和重绘压力；
4. 生成期间仍会执行会话列表刷新等旁路工作；
5. Rust 侧仍存在逐分片字符串分配和缓冲区复制等低优先级开销；`reqwest::Client` 已由共享本机 Runtime 复用。

## 3. 总体原则与非目标

### 3.1 原则

- 保持 `/api/chat`、`think`、`num_ctx`、`num_predict`、历史裁剪和思考保存策略不变；
- 首个有效分片和最终分片优先，不能因为批处理而明显延迟首字或丢失尾部内容；
- 保留 `request_id` 校验、取消、错误传播和迟到旧请求过滤；
- 先测量，再逐阶段改变行为，每次只引入一类主要变量；
- 性能诊断只保存在本地调试结果，不保存提示词、回答、思考内容，不引入遥测；
- Debug 和 Release 均可验证，最终验收以 Release 为准。

### 3.2 非目标

- 不通过降低输出上限、关闭思考或缩短历史来制造客户端变快的假象；
- 不更换模型、量化、Ollama 服务或传输协议；
- 不引入重量级 Markdown 编辑器、虚拟列表库或后台联网服务；
- 不在一次提交中同时重写 Rust 流、React 状态和 SQLite 存储。

## 4. 测量定义与共同测试条件

### 4.1 时间点

所有阶段使用相同的时间定义：

| 标记  | 定义                          |
| --- | --------------------------- |
| T0  | 用户点击发送或按 Enter              |
| T1  | 前端开始执行发送流程                  |
| T2  | Rust 发出 HTTP 请求             |
| T3  | Rust 收到 Ollama 首个 NDJSON 分片 |
| T4  | 前端收到首个 `chat:chunk`         |
| T5  | 首个思考字符或正文字符完成一次实际绘制         |
| T6  | 首句或约 20 个正文字符完成绘制           |
| T7  | 收到并绘制最终 `done` 事件           |
| T8  | 回复保存和必要的会话列表刷新完成            |

当前 UI 的 `wallMs` 是从用户消息保存之后才开始计算的，不等于完整的 T0→T7；优化期间必须同时记录用户感知时间和模型服务时间。

### 4.2 固定条件

- 同一 Windows 设备、同一 Ollama 版本和模型 digest；
- 模型常驻与首次加载分开测试；
- 固定提示词、历史消息和思考显示策略；
- 使用快速、平衡、推理三档分别测试；
- `temperature`、`num_ctx`、`num_predict`、`think` 与客户端实际请求一致；
- 每个 A/B 版本每档至少 8 个有效样本，采用交替或随机顺序；
- 记录 `load_duration`、`prompt_eval_duration`、`eval_duration`、`eval_count`、首块时间和事件数量；
- 测试期间关闭其他会访问 Ollama 的客户端，接通电源并固定电源模式。

## 5. 阶段 0：链路诊断与可重复基线

### 实施方案

1. 在 Rust 流处理器记录请求级和分片级调试指标：请求发出、首字节、首个完整 NDJSON 行、每次 emit、最终 emit、分片序号、累计字节数和事件数量。
2. 在前端记录 T0、`listen` 回调进入、合并缓冲、React commit 和 `requestAnimationFrame` 绘制时间。
3. 使用 `React.Profiler` 或等价的本地调试标记记录当前消息组件和历史消息组件的渲染次数与耗时。
4. 使用浏览器 `PerformanceObserver` 记录 50ms 以上长任务；不记录内容正文。
5. 诊断字段使用可选字段或调试构建开关，Release 默认关闭；不改变现有 `ChatStreamPayload` 的正文语义。
6. 建立基线报告，至少包含：事件数、总 payload 字节、前端 flush 数、T3→T5、T5→T7、T0→T7 和服务端 `eval_duration`。

当前实现的开关约定：Rust Debug 构建默认发出诊断事件；设置 `OLLMIN_DIAGNOSTICS=0` 可关闭，Release 需要显式设置 `OLLMIN_DIAGNOSTICS=1` 才会发出。前端开发模式默认收集诊断，Release 可在 WebView 控制台执行 `localStorage.setItem("ollmin:diagnostics", "1")` 后重新发起请求；记录保存在 `globalThis.__OLLMIN_DIAGNOSTICS__`，只包含时间、计数和长度，不包含提示词、正文或思考内容。

### 测试方法

- 运行现有 TypeScript、Rust 单元测试；
- 用固定短问题和固定思考问题分别测三档；
- 每档执行 8 次，API 控制组与 Ollmin Release 交替执行；
- 额外测试 4–6 轮长历史，观察消息数量增加时的渲染次数；
- 对比 Debug/Release 的事件数和前端渲染耗时；
- 检查诊断数据中不出现提示词、正文或思考内容。

### 验收目标

- 能稳定区分 T0、T2、T3、T4、T5、T7、T8；
- 能得到每个请求的事件数量、首分片延迟和 UI commit/paint 延迟；
- 同一请求的事件序号连续，无遗漏或重复；
- 诊断开关关闭时，用户界面和请求 payload 与基线一致；
- 形成一份基线报告，作为后续阶段唯一对照。

## 6. 阶段 1：前端按帧合并流式更新

### 实施方案

1. 保留现有 `assistantBuffer` 作为增量累积区；`listen` 回调只追加 `content`、`thinking` 和最终 metrics，不再每个分片立即调用 `setMessages`。
2. 增加一个待刷新标记和 `requestAnimationFrame` 调度器；一帧内的多个分片合并成一次 React 状态更新。
3. 首个有效思考/正文分片立即 flush；普通分片按 16–33ms 合并；`done`、错误和取消事件立即 flush。
4. flush 时只更新当前 assistant 消息，保持其他消息对象引用不变。
5. 在组件卸载、新请求开始、取消和终止事件时清理 pending frame/timer，避免旧请求污染新请求。
6. 不改变 `ChatStreamPayload` 的增量语义，确保每个分片仍被完整拼接。

### 测试方法

- 为流式聚合器补充单元测试：单分片、多分片同帧、跨帧、首片、最终片、错误、取消、旧请求；
- 使用假的事件序列验证最终正文、思考内容和 metrics 与未合并版本完全一致；
- 使用 React Profiler 比较基线和候选版本的 commit 次数；
- 在 Release 中运行三档短回答和思考回答，记录 T4→T5、T5→T7、长帧和可见停顿；
- 进行至少一次取消后立即发起新请求的回归测试。

### 验收目标

- 输出正文和思考内容 0 丢失、0 重复、0 乱序；
- 首个可见字符相对基线增加不超过 16ms（P50）或 50ms（P95）；
- React commit 次数至少下降 70%；
- 普通流式更新频率稳定在 30–60 次/秒，不出现连续超过 100ms 的人为停顿；
- 取消、错误、迟到事件过滤和最终 metrics 正常；
- 快速模式的客户端首字额外开销仍满足 150ms 目标。

## 7. 阶段 2：消息组件隔离与渲染记忆化

### 实施方案

1. 将 `messages.map(...)` 中的单条消息 DOM 抽为 `MessageItem` 组件。
2. 使用 `React.memo(MessageItem)`，让未变化的历史消息跳过渲染。
3. 将思考区抽为独立的 `ThinkingBlock`，将正文抽为独立的 `MarkdownContent` 子组件；思考变化时不重新解析正文。
4. 对 `MarkdownContent` 使用浅比较记忆化；仅当正文字符串变化时重新执行 Markdown 解析。
5. 保持 `MessageItem` 的 key、复制按钮、错误状态、取消状态和展开状态不变。
6. 如果 Profiler 证明长历史仍明显占用 CPU，再评估按消息数量启用轻量虚拟化；本阶段不直接引入第三方虚拟列表。

### 测试方法

- 为 `MarkdownContent` 保留现有格式测试，并增加思考变化时正文不重新渲染的组件测试或 Profiler 断言；
- 准备 1、10、30 条历史消息和短/长 Markdown 回答；
- 分别在正文流、思考流和混合流下记录历史组件渲染次数；
- 检查滚动区域、复制、代码块、列表、标题和深色模式；
- 在低性能设备上测量长历史场景的 T5→T7 和长帧数量。

### 验收目标

- 流式更新期间，未变化的历史消息组件不重复渲染；
- 仅思考变化时，正文 Markdown 不重复解析；
- 长历史场景的前端渲染 CPU 时间降低至少 50%；
- 不出现消息闪烁、滚动跳动、思考内容丢失或复制按钮失效；
- 现有 `npm run build` 与 `npm run test` 通过。

## 8. 阶段 3：Rust 侧分片批处理与解析优化

### 实施方案

1. 在 `run_chat_stream` 中增加有界 pending batch，合并同一时间窗口内的正文和思考增量。
2. 默认以 16–33ms、最大字节数和终止事件三者之一触发 flush；首个有效分片直接 flush。
3. 最终 `done` 事件必须携带所有 pending 增量、Ollama response metrics 和正确的终止状态。
4. 增加 `sequence` 或等价的调试序号，便于发现丢片、重复和乱序；生产 payload 只在诊断开关开启时携带额外字段。
5. 使用 `BytesMut` 或等价的无额外复制缓冲方式；使用 `serde_json::from_slice` 解析完整行，减少 `String::from_utf8_lossy`、`trim` 和 `to_string` 分配。
6. 移除不必要的 `ChatMessage` clone，但保留最终 metrics 序列化和错误处理所需的数据所有权。
7. 保持取消 token 的优先级：等待下一个网络分片、批处理等待和发送前都必须响应取消。

实现开关：默认启用 Rust 侧批处理；调试 A/B 或需要快速回退时，将进程环境变量
OLLMIN_STREAM_BATCHING=0 设置为关闭批处理，恢复逐分片发送，不改变 Ollama 请求参数。

### 测试方法

- 为 NDJSON 解析补充：多行同一 bytes chunk、半行、CRLF、空行、最后无换行和 malformed JSON 测试；
- 为批处理器补充：时间触发、字节数触发、首片立即发送、done 强制发送、取消/错误 flush 测试；
- 使用录制的 NDJSON fixture 对比批处理前后的最终正文、思考和 metrics；
- 对比 Rust emit 事件数量和 Tauri 前端收到的事件数量；
- 在本机 Ollama 上用三档各运行至少 8 次，比较模型 `eval_duration` 是否保持在统计误差范围内。

### 验收目标

- 事件数量相对基线减少至少 70%，目标为 4–10 倍减少；
- 内容、思考、done、错误和取消语义完全一致；
- 首个有效事件额外延迟不超过 16ms（P50）/50ms（P95）；
- 批处理造成的最大可见间隔不超过 100ms；
- Rust 单元测试、`cargo fmt -- --check` 和 `cargo test` 全部通过；
- 不因批处理改变 Ollama 服务端 `eval_duration` 或输出 token 数。

## 9. 阶段 4：请求前后旁路工作和连接复用

### 实施方案

1. 将 T0、用户消息保存、`start_chat` 调用和首个事件分别计时，确认真实用户等待中各段占比。
2. 对新会话评估新增一个 Rust 事务命令，将“创建会话 + 保存用户消息”合并，避免两个 Tauri invoke 和两次数据库锁获取。
3. 将发送后立即执行的 `loadConversations(search)` 延迟到首个响应或最终保存后，避免生成初期触发无关列表查询和 React 更新。
4. 保持侧边栏新会话可见性：必要时只更新当前会话摘要，不重新查询包含全文搜索的全部列表。
5. 将共享 `reqwest::Client` 放入 `ChatState` 或进程级单例，复用本地 HTTP 连接池；不改变 Ollama 地址和请求内容。
6. 评估 SQLite 的消息保存和会话更新时间是否需要单事务，但不改变级联删除、迁移和隐私边界。

### 测试方法

- 对比新建会话和已有会话两条路径的 T0→T2；
- 在生成期间观察会话列表是否仍能正常显示和搜索；
- 断电式异常不可模拟时，至少测试请求取消、Ollama 断线和数据库错误；
- 验证共享 Client 不会复用错误的请求状态，多个请求仍被 active lock 正确串行；
- 运行 SQLite 迁移、级联删除、消息保存和隐私边界测试；
- 对比连接复用前后的首请求/热请求差异，若低于测量噪声则不保留复杂改动。

### 验收目标

- 新会话 T0→T2 的中位数减少至少 20ms，或有明确测量证据表明该路径不是瓶颈；
- 生成开始阶段不再执行非必要的完整会话列表刷新；
- 会话创建、用户消息保存、取消、错误和重启恢复不回归；
- SQLite 数据结构和现有隐私行为不改变；
- `reqwest::Client` 复用不改变模型服务端统计和请求参数。

## 10. 阶段 5：Release A/B 验证与发布

### 实施方案

1. 保留基线实现和候选实现的可切换开关，完成各阶段单独 A/B 后再合并默认行为。
2. 重新构建 Debug 和 Release；Debug 用于日志，Release 用于用户体验结论。
3. 使用固定模型、固定提示词、固定历史和交替执行顺序，分别测试快速、平衡、推理。
4. 将服务端指标、Rust/IPC 指标、React commit/paint 指标和用户感知 T0→T7 放在同一份报告中。
5. 进行回归检查：停止、错误、迟到事件、切换会话、切换主题、复制、导出、SQLite 保存和应用重启。
6. 若候选版本出现首字变慢、长停顿或内容不一致，按阶段开关回退，不整体回退到无法定位的混合版本。

### 测试方法

- 每个模式每个版本至少 8 个有效样本，P50、P95 和配对差值同时报告；
- 热模型短问题、思考型问题、长历史和首次请求分开统计；
- 至少一次低性能设备或高 CPU 负载场景；
- 对照原生等价 API，确认服务端 `eval_duration` 没有被客户端改动影响；
- 运行：

```powershell
npm run build
npm run test
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --manifest-path src-tauri/Cargo.toml
npm run tauri -- build --debug
npm run tauri -- build
```

### 总体验收目标

- Tauri/前端链路的客户端额外首字开销：P50 ≤ 16ms，P95 ≤ 50ms；
- 快速模式客户端额外首字开销继续满足阶段 0 的 150ms 目标；
- 平衡和推理模式的 GUI 总耗时相对等价 API 的额外开销中位数 ≤ 300ms；
- 前端事件/commit 数量至少减少 70%；
- 低性能设备上长帧和超过 500ms 的可见停顿明显减少；
- 服务端 `eval_duration`、输出 token 数、思考字段和请求参数不被改变；
- 所有现有功能和隐私边界回归测试通过；
- 生成一份不包含提示词和模型回答的最终性能报告。

## 11. 风险、回滚与停止条件

### 主要风险

- 批处理窗口过长导致首字或正文首句变慢；
- flush 状态机在 done、取消或错误时丢失 pending 增量；
- React 记忆化导致状态、复制或思考展开显示不同步；
- 延迟会话列表刷新后，侧边栏短时间显示旧摘要；
- Rust 连接复用造成请求取消或错误状态交叉污染。

### 回滚策略

- 阶段 1 和阶段 3 均保留 `batching=false` 的调试回退开关；
- 每阶段单独提交，禁止将多个未验证阶段合并成一个不可逆提交；
- 发现内容丢失、顺序错误、取消失效或首字 P95 回退超过 50ms 时，立即关闭该阶段开关并保留诊断报告；
- 不通过删除会话、重置数据库或改变模型参数来掩盖回归。

## 12. 推荐实施顺序

```text
阶段 0 诊断基线
   -> 阶段 1 前端按帧合并
   -> 阶段 2 消息组件记忆化
   -> 阶段 3 Rust 分片批处理
   -> 阶段 4 请求旁路与连接复用
   -> 阶段 5 Release A/B 验证
```
