# Ollmin 与 Ollama CLI 的真实用户感知性能测试方案

> 状态：待执行的测试方案。当前代码已具备部分诊断事件与流合并实现，但本文件不包含可复核的测量结果；在采集同条件 Release 数据前，不应据此声称 Ollmin 已达到任何用户感知延迟目标。

## 目标

比较真实用户使用 Ollmin Release 客户端与 `ollama run` CLI 时感受到的等待速度、首段可读内容到达时间和流式输出顺滑度，并区分下列来源：

- 模型加载、预填充与解码；
- Ollmin 的 Tauri 流转发、前端状态更新和内容渲染；
- CPU 调度、电源策略、温度与后台负载；
- 思考展示和会话历史造成的真实产品差异。

本方案以真实 Ollmin 窗口为被测对象。原生 `/api/chat` 仅作为控制组，用于判断差异是否发生在客户端之外；不能用它代替 GUI 测试结果。

## 测试对象与公平边界

被测对象：

1. Ollmin Release 客户端；
2. `ollama run` CLI；
3. 原生 `/api/chat` 流式请求（控制组）。

每组测试必须固定：

- Ollama 版本、模型完整名称和 digest；
- 模型常驻状态；
- 同一模式的 `think`、`num_ctx`、`num_predict`、温度与输出上限；
- 相同的系统提示、消息历史和最终用户问题；
- 单请求运行、无其他客户端访问 Ollama；
- 接通电源，固定 Windows 电源模式，并记录后台活动。

优先固定随机 seed；若当前版本无法稳定固定，则使用 `temperature=0`，并记录每轮的输出 token 数和思考字符数。

公平性验收条件：两端 Ollama 返回的 `prompt_eval_count` 应基本一致。若差异超过约 1--2 token，则说明实际送入模型的上下文不同，该轮样本作废，不用于客户端速度结论。

## 用户感知指标

每次请求以用户按下 Enter 或点击“发送”的时刻为 T0，记录以下时间点：

| 指标 | 含义 |
| --- | --- |
| T0 | 用户提交请求 |
| T1 | 界面或终端出现“已开始生成”的反馈 |
| T2 | 首个可见字符出现；思考模式下可为首个思考字符 |
| T3 | 首个正文字符出现 |
| T4 | 首句或约 20 个正文字符出现，用户可开始阅读和判断价值 |
| T5 | 完整回复结束 |
| Stall P95 | 相邻可见更新间隔的 P95，衡量持续输出的卡顿感 |
| 可见停顿次数 | 超过 500 ms 没有可见更新的次数 |
| 长帧次数 | Ollmin 中超过 50 ms 的浏览器渲染帧数 |

同时记录 Ollama 的 `load_duration`、`prompt_eval_duration`、`eval_duration`、`prompt_eval_count` 与 `eval_count`。其中 T3、T4、T5 和 Stall P95 是主要体验指标；单独的 token/s 不能代表用户更早读到可用回答。

## 测试场景

每种性能模式分别对比 CLI 和 Ollmin，不把三种模式混合平均。

| 场景 | 目的 | 覆盖模式 |
| --- | --- | --- |
| 热模型、短问题 | 衡量最常见的即时问答体验 | 快速、平衡、推理 |
| 热模型、思考型任务 | 放大思考流、分片转发与渲染压力 | 平衡、推理 |
| 热模型、固定长历史 | 验证真实多轮会话的上下文与预填充影响 | 快速、平衡、推理 |
| 首次请求 | 单独衡量加载与初始化；不与热模型混合比较 | 可选，三档均可测 |

长历史使用固定的 4--6 轮用户/助手消息。CLI 必须收到与 Ollmin 最终实际发送的完全相同的消息：快速模式按产品规则裁剪，平衡和推理模式保留完整历史。这样衡量的是用户实际会获得的产品体验，而非人为改变模式行为后的理论速度。

思考展示策略必须单独测试，且两端保持一致：

- **思考可见**：CLI 与 Ollmin 都显示思考过程；
- **正文优先**：CLI 与 Ollmin 都隐藏或折叠思考过程。

不得把“一个客户端显示数百个思考分片、另一个客户端不显示”的结果混为速度差。

## 执行流程

1. 记录系统、Ollama、模型、处理器卸载信息和电源状态；关闭其他会调用 Ollama 的程序。
2. 对每个“模式 × 场景 × 客户端”先进行 1 次预热，不计入统计。
3. 取得 8--10 个通过公平性验收的正式样本。
4. 随机并交替执行客户端，禁止连续完成一侧再执行另一侧。例如：`CLI → Ollmin → Ollmin → CLI → CLI → Ollmin`。
5. 每轮间隔固定的短暂停顿；记录测试顺序、模型是否常驻、CPU 占用/频率/温度（若设备可读取）和后台活动。
6. 计算每项指标的中位数、P95、配对差值与有效样本数；不使用三次样本的 P95 作稳定性结论。

首次请求属于单独分组。不要通过自动执行 `ollama stop` 制造冷启动，以免中断用户其他任务；只在专用空闲环境中，由操作者明确确认后测试。

## 采集方式

### 用户界面与终端

使用 60 fps 屏幕录制复核 T0--T5 和可见停顿。CLI 的时间从提交命令到终端出现字符计算；Ollmin 的时间从发送动作到窗口中对应内容可见计算。录像是无需改变产品即可执行的基线方法。

### 推荐的测试诊断采集

后续可加入仅测试可用的本地诊断记录，不改变正常聊天逻辑：

- 前端：记录 T0、每个 `chat:chunk` 事件接收时间、React 提交时间、首个实际绘制时间与 T5；
- Rust：记录向 Ollama 发起请求、收到首个 NDJSON 分片、转发最终分片的时间；
- CLI：由包裹脚本记录命令提交、首个标准输出字节和进程结束时间。

诊断数据只保存时间戳、长度和 Ollama 指标，不保存提示词、思考内容或模型正文。屏幕录像和诊断记录互相校验；若二者不一致，以可见画面作为用户体验结论。

## 小型盲测

在完成可重复的仪器测试后，邀请 6--10 位使用者完成相同任务。随机安排客户端顺序：一半参与者先使用 Ollmin，另一半先使用 CLI；不告知当前客户端身份。

每轮完成后，由参与者对下列项目打 1--7 分：

- 多久开始感觉系统已在工作；
- 多久开始看到有用内容；
- 输出是否顺滑、是否出现卡顿；
- 总体等待是否可接受。

主观评分仅用于解释体验感受，不能替代客观时序数据。

## 结果判定

| 观察结果 | 优先排查方向 |
| --- | --- |
| 服务端 `eval_duration` 接近，但 Ollmin 的 T3/T4/T5 更晚且长帧更多 | Tauri IPC、React 状态更新或 Markdown 重绘 |
| 两端服务端 `eval_duration` 已显著不同 | CPU 调度、温度、电源状态、模型运行状态，或请求参数未真正对齐 |
| 仅思考可见时 Ollmin 更慢 | 思考分片的 UI 更新压力 |
| 仅长历史时 Ollmin 更慢 | 历史裁剪策略、实际消息数或上下文预填充 |
| T3 接近但 T5 差异大 | 持续流式渲染或输出阶段的资源竞争 |
| T1/T2 已明显更晚 | 请求发起、进程调度或首分片传递 |

测试报告必须明确标注：所测的是热模型还是首次请求、思考是否可见、是否真实 GUI、有效样本数与被作废的样本数。只有在服务端参数和上下文已经对齐后，才能把剩余差异归因于客户端。
